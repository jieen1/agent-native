# 07 · 自举实战的根因聚类与 v2.2 设计修订（权威）

> 2026-07-11 用真实系统跑通 B1–B3 三单（含派发、vLLM 开发、brain 评审、
> 人工评审、合并、阶段推进）后，沉淀出 SDLC-037~058 共 20+ 个观察问题。
> 本章不罗列补丁——把问题聚类回**设计盲区**，回答三件事：
> ① 根因是什么、v2.1 为什么没想到；② 哪些属于"设计有、实现欠账"
> （不改设计，照设计做即可）；③ 哪些是设计本身缺失（v2.2 已在对应章节
> 补上机制级对策，本章给索引）。

## 0. 总根因：只设计了"角色做什么"，没设计"环境保证什么"

v2.1 把设计精力放在角色、流程、页面（发生在**前台**的事），把执行基底
（工作区、权限、遥测、标识、状态写入权）当作"引擎自然会做对的事"。
自举证明：**凡是没有写成契约/不变量的环境性质，都会以最坏的方式失效**。
v2.2 的修订原则由此而来（00 章 P13）：**机制优先于提示词**——凡红线，
必有一个技术机制背书（能力面裁剪 / 写入守卫 / 引擎断言 / 显式告警），
提示词只承担解释职责。

## 1. 十个根因簇

### 簇一：工作区契约缺失

- **涉及**：SDLC-056(1f2igmbdch 基线过期)、SDLC-057(无测试执行环境)、
  SDLC-044(TDD 证据无从产生的使能条件)；v2.2.1 追加 SDLC-059
  （workspaceDiff 静态基线→W4 观测基线正确性）、SDLC-061
  （自建表测试掩盖迁移缺失→迁移冒烟证据档）。
- **现象**：B2 工作区基于 3 天前的 main 造成合并冲突；vLLM dev 自述
  「环境无 vitest 二进制,无法执行测试」，红绿循环纸上谈兵。
- **根因**：v2.1 设计了 DAG 节点与角色，但"工作区"从未被当作有供给规范的
  一等对象——基线新鲜度、依赖可用性、测试可执行性都没有验收条件。
  为什么没想到：设计视角站在"任务流"上，把 workspace 当成 `workspaceCreate`
  的实现细节，而它实际是 dev/qa/reviewer 三个角色的**全部世界**。
- **对策（02 §7 工作区契约）**：工作区就绪的三条验收不变量（基线=派发时
  镜像 main、依赖已预热、`test_cmd_smoke` 可运行）；staleness 事件与交付前
  rebase 断言；"测试不可执行"定性为 infra 故障而非 agent 责任。
  质量调研佐证：B3 在补齐环境后 311 测全绿一次通过——测试可执行不是
  奢侈品，是本来就该有的强制基线。

### 簇二：能力边界靠提示词而非机制

- **涉及**：SDLC-052(brain 直改/整文件重写工作区源码)、SDLC-055 的一半
  （评审不在 DAG 上，越界行为无处审计）。
- **现象**：brain 在评审相位先 `printf >>` 补换行，后误 `git checkout --`
  回退 dev 产出、再用 Write 整文件重写——最终合入代码的作者身份已经不是
  vLLM。提示词红线全程在场，没拦住任何一步。
- **根因**：红线只存在于 BRAIN_PROMPT 与 memory，brain 的工具面
  （Bash/Write/Edit 全开）与文件系统权限（工作区可写）从未按相位收缩。
  为什么没想到：v2.1 §5.3 写了"不做代码直改"，并给了**可观察指标**
  （workflowRun 计数），但把"可观察"当成了"已约束"。观察≠约束。
  质量调研补充了同类第二例：B2 评审期 brain 顺手跑 oxfmt 全文件格式化
  →误伤回滚→手工重写，"顺手修复"的每一步都在放大作者身份转移。
- **对策（02 §5.4 能力面矩阵 + 00 P13）**：角色×相位的能力面矩阵成为
  引擎配置（评审相位 brain 的 workspace 只读挂载/写类工具裁剪；修复必须
  重派 dev 节点 fix 模式）；越界操作机制上不可为，审计告警兜底。

### 簇三：状态迁移无守卫、无必带证据

- **涉及**：SDLC-056(5rmlahjmxg B3 未经评审即 done)、SDLC-045(终态不推进)、
  SDLC-053(回链恒空/不随重派更新)、SDLC-044(测试证据未强制)、
  以及"未派发项无任何关闭通道"（B 面：该守卫的地方无守卫，该有通道的
  地方无通道）；v2.2.1 追加 SDLC-063（派发即推进阶段、失败不回退→
  守卫表新增派发行：业务阶段不因派发而推进）。
- **根因**：v2.1 设计了门判据（gate criteria），但从未回答两个更基础的
  问题：**每个状态迁移允许谁写**、**迁移必须携带什么证据载荷**。
  为什么没想到：门判据设计源自"相位推进"视角（sprint 级），工作项级的
  status/stage 写入被默认为"实现自然会管好"。
- **对策（02 §8 状态迁移守卫表）**：每个迁移一行——合法写入方、必需证据
  工件、失败行为；`done` 只能由带 PASSED verdict 的评审记录驱动，agent
  交付只能到「待人工评审」；回链（runId/branch）是迁移载荷的必填字段，
  重派=新迁移=同步更新；补人工流转/关闭 action（守卫内的例外通道，
  强制 reason+审计）。

### 簇四：遥测与身份无单一事实源

- **涉及**：SDLC-051(token 遥测失真)、SDLC-054(一模四名)、SDLC-049
  (harness 静默降级)、SDLC-046/048(模型窗口与目录漂移)；v2.2.1 追加
  SDLC-057(x5np，64k 静默钳制→配置生效一致性告警)、SDLC-060
  (线程交付成功却标 error→turn 终态判定契约，04 §6)。
- **现象**：同一份 27B 权重以 4 个名字服务（含两个 claude-\* 假名）；
  spawn 的 tokens_output 物理不可能、tokens_input 恒 0；ACP 包被重部署
  抹掉后 brain 静默换引擎跑了一整天。
- **根因**：模型身份、用量、引擎形态三样"归因赖以成立的事实"各自散落，
  没有权威登记处，坏数据与假名不会被任何断言拒绝。为什么没想到：
  v2.1 的引擎注册表（02 §5.1）设计了 health/capabilities 字段，但把
  "模型叫什么"与"用量怎么采"当作显然正确的输入。
- **对策（04 §7 模型注册表 + §10/§13 采集契约）**：模型注册表登记真名+
  别名映射+档位，禁止非 Claude 权重使用 claude-\* 名（注册表校验）；
  用量采集契约（只取流终 usage、input 必填、超物理速率即标记 suspect
  不入度量）；降级显式化不变量——**声明开启的能力初始化失败 = 健康页
  红卡 + 线程 degraded 徽标，静默降级本身定性为缺陷**。

### 簇五：引擎终态传导不完备

- **涉及**：SDLC-050(spawn 重置后节点悬挂 running、不可 retry 不再入队、
  runCancel 报错但生效)。
- **根因**：v2.1 的 R1（孤儿降级）设计的是"进程重启"场景，漏掉了
  "reconcile 判死 spawn"这条终态来源——spawn 的任何终态从哪来都必须
  传导到 node 状态机，这个**不变量**没写成设计承诺。
- **对策（02 §4 R9）**：新增恢复语义 R9——"不存在 spawn 已终态而其
  node 仍 running 超过一个 tick"为引擎不变量，违反即 reconciler 修正+
  告警事件；runCancel 幂等、成功必须返回成功。

### 簇六：人工工作流未在 UI 一等化

- **涉及**：SDLC-056(5rmlahjmxg)的 UI 面、SDLC-029(UI 可触发性审计)、
  本次自举的直接体感——人工评审/合并/建 issue/关 sprint 全程走 SSH+MCP，
  S3/S5 页面一次都没用上。
- **根因**：v2.1 给"人"设计的 UI 集中在签核与裁决（收件箱），但自举里
  人的高频动作是**评审 agent 交付的代码**与**管理问题池**——这两个动作
  没有页面路径。为什么没想到：设计时人扮演的角色被想象成"审批者"，
  实战中人是"评审员+策展人"。
- **对策（03 §2/§4/§6）**：收件箱新增**评审请求**类别（锚定分支 diff、
  测试证据、审查三问，操作=批准合并/驳回返工，接 02 §9 的待人工评审
  迁移）；工作项详情状态 PropRow 变为受守卫流转入口（含未派发项关闭）；
  规划工作台增设观察问题池泳道（backlog 观察项拖入 sprint 即挂载）。
  验收标准升格：**流程中每个人工动作必须有页面路径，SSH/MCP 仅是
  自动化通道而非唯一通道**。

### 簇七：全局标识无分配权威

- **涉及**：SDLC-038(itemKey 跨 sprint 重号——本章写作当天再次复发：
  两个不同 issue 同挂 SDLC-056)、SDLC-037(迁移版本号跨分支静默碰撞)。
- **根因**：itemKey 与迁移版本都是"顺序小整数"，由各写入方自行取
  max+1——并行分支/并发写入下必然撞号，撞号后（迁移场景）还被静默跳过。
  为什么没想到：单人单线开发中 max+1 从不出错，设计未把"并行 agent
  同时分配标识"当作常态。
- **对策（02 §8 末条 + 03 §11）**：一切全局单调标识必须有单点分配权威
  ——itemKey 由 tracker 项目级序列器在 create 时唯一分配（DB 序列/
  advisory lock，不由调用方报数）；迁移登记以内容哈希+命名空间为身份，
  数字序仅在合并线性化时由单点重排；撞号必须失败出声，禁止静默跳过。

### 簇八：spec 作者 = 评审者的结构性盲区（质量调研新增）

- **涉及**：B2 非事务三连写、B3 N+1 查询与吞异常——三者**都是 brain 自己
  写进 spec 的设计决定**，brain 评审对应 diff 时零命中（评审转录全文检索
  "事务/批量"零命中）。
- **反证**：M3-D 单（brain 评审**他人**遗留代码）抓出 5 个真 bug，含
  critical 逻辑错误与 ownerScope 绕过——评审能力没问题，**结构**有问题：
  没有人会质疑自己十分钟前做出的设计决定。
- **根因**：v2.1 的 reviewer 节点设计了"多轮对抗、累计发现清单"，但没
  规定评审者与 spec 作者的**身份分离**——brain 既写 spec 又审 diff 时，
  spec 本身的缺陷成为评审的盲区。为什么没想到：设计把评审对象想成
  "代码 vs spec 的偏离"，漏了"spec 本身错了"这一失效模式。
- **对策（02 §3 公共约束 + §5.4）**：**评审独立性规则**——reviewer 会话
  必须独立于 spec 作者（新会话/独立 agent，输入=需求原文+spec+diff，
  明确要求对抗性质疑 spec 的设计决定，而不只对照实现偏离）；
  gap-analysis 同理（判定基准是 Goal 而非 spec，天然独立，维持）。

### 簇九：任务规模无分流阈值（质量调研新增）

- **涉及**：M3-D（655 行 spec）与 S0（846 行 spec）两单 12 文件级任务，
  vLLM 连续 3 次输出预算耗尽、6 个线程才交付，brain 被迫代写 4 个文件
  （作者身份转移的另一条成因链）；对照 B1–B3（1–6 文件+伪代码级 spec）
  全部扎实一次交付。
- **根因**：v2.1 工作流选择器按**类型**分流（缺陷/文档/调研…），从未按
  **规模**分流；A10 假设写了工作项粒度 2–6 小时，但没有任何机制在
  规划期强制它。为什么没想到：把"拆小"当成人的习惯，而不是系统契约。
- **对策（02 §3.10 拆分契约 + 03 §6）**：规划/派发前的**拆分契约**——
  spec 涉及 >6 个文件、或跨生命周期协同（如 schema+action+页面+调度器
  联动）时，强制拆为多个 dev 子任务（issue-pipeline 多节点或多工作项），
  规划工作台在 extract-briefs 结果卡上给出规模告警与一键拆分入口；
  vLLM 单节点输出预算耗尽 ≥2 次自动定性为"规模超标"，回规划拆分而非
  换更大模型硬扛。

### 簇十：dev 执行器无上下文管理（质量调研 + M3-D 根因追问确认）

- **涉及**：M3-D/S0 两单连续输出预算耗尽的**执行器侧根因**（与簇九的
  规划侧根因互补）。
- **现象**：vLLM dev 节点（engine-loop.ts → runAgentLoop）是一根裸循环
  ——消息只增不减：每次 Read 的文件全文、每轮 thinking token 全部滞留
  在窗口里，没有任何压缩/剪枝/摘要；溢出 262k 物理窗口即截断失败；
  attempt 重试**从零重跑同一任务**→确定性再次溢出，无断点续写。
- **根因**：brain（CC）自带自动 compaction，worker 没有——**worker 与
  brain 的上下文能力不对等**，而设计把"执行一个 dev 任务"当作单次
  prompt-response 的放大版，从未考虑执行器的上下文生命周期。
  为什么没想到：v2.1 的恢复语义（R1–R8）全部着眼于**进程与状态**的
  恢复，没有一条关于**上下文窗口**这一 worker 最稀缺资源的管理。
- **对策（02 §4.1 执行器上下文契约）**：① dev 循环必须有上下文管理
  （工具结果窗口化、读文件按需截取、超阈值自动摘要折叠）；② 截断失败
  的重试语义 = 携带已完成产物**续写**（R4 检查点重试延伸到上下文场景），
  不是从零重跑；③ 与簇九拆分契约互补——拆分降低需求，上下文管理保底。

## 2. "设计已有、实现欠账"清单（不改设计，按设计做）

自举暴露的问题里有一部分 v2.1 已有正确设计，失效是因为实现尚未跟上——
这类**不属于设计盲区**，逐条对照防止误改设计：

| 问题                              | v2.1 已有设计                                      | 差距性质                                                  |
| --------------------------------- | -------------------------------------------------- | --------------------------------------------------------- |
| SDLC-045 终态不推进               | 02 §6 回写通道（reconciler 主 + 轮询兜底）         | 回写通道未建（M4-D 在册）                                 |
| SDLC-056 基线过期的**合并时**防线 | 02 §3.1 merge-pr 节点断言 merge-base==sprint-tip   | 单节点 sdlc-dev 尚无 merge 节点；且创建时新鲜度属簇一新增 |

## 4. 对"不可能再发生 / 发生即可见"的逐簇答复

| 簇  | 机制生效后                                                                                     |
| --- | ---------------------------------------------------------------------------------------------- |
| 一  | 基线陈旧/无测试环境的工作区**通不过就绪断言**，run 根本不会开始（不可能发生）                  |
| 二  | 评审相位 brain 无写路径，直改**机制上不可为**；万一绕过（新工具面漏洞）审计告警（发生即可见）  |
| 三  | 非法写入方/缺证据的迁移被守卫**拒绝**（不可能）；人工例外通道强制 reason 留痕（可见）          |
| 四  | 假名模型注册即被拒（不可能）；用量异常标记 suspect 不污染度量（可见）；降级=红卡+徽标（可见）  |
| 五  | 悬挂节点被 R9 不变量在一个 tick 内修正并告警（可见且自愈）                                     |
| 六  | 人工动作有页面路径，UI 可触发性成为每功能验收标准（缺口在验收时即暴露）                        |
| 七  | 标识由单点分配，撞号在分配时即失败出声（不可能静默）                                           |
