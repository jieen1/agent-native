## 0. 总根因：只设计了"角色做什么"，没设计"环境保证什么"

v2.1 把设计精力放在角色、流程、页面，把执行基底（工作区、权限、遥测、标识、状态写入权）当作"引擎自然会做对的事"。自举证明：**凡是没有写成契约或不变量的环境性质，都会以最坏的方式失效**。v2.2 的修订原则由此而来（00 章 P13）：**机制优先于提示词**——凡红线，必有一个技术机制背书（能力面裁剪、写入守卫、引擎断言、显式告警），提示词只承担解释职责。

## 1. 十个根因簇

### 簇一：工作区契约缺失

B2 工作区基于 3 天前的 main 造成合并冲突；vLLM dev 自述「环境无 vitest 二进制，无法执行测试」，红绿循环纸上谈兵。根因：工作区从未被当作有供给规范的一等对象——基线新鲜度、依赖可用性、测试可执行性都没有验收条件。对策：02 章「工作区契约」三条就绪不变量（W1 基线新鲜 / W2 依赖预热 / W3 测试可执行），staleness 事件与交付前 rebase 断言，测试证据为交付前置。佐证：B3 补齐环境后 311 测全绿一次通过。（SDLC-056/057/044）

### 簇二：能力边界靠提示词而非机制

brain 评审时先 printf 补换行，后误 checkout 回退 dev 产出、再整文件重写；另一单顺手跑全文件格式化→回滚自伤→手工重写。提示词红线全程在场，没拦住任何一步。根因：brain 的工具面与文件系统权限从未按相位收缩——把"可观察"当成了"已约束"。对策：02 章「能力面矩阵」（角色×相位→工具面与 workspace 权限成为引擎配置；评审相位只读挂载，修复只能重派 dev fix 模式）。（SDLC-052/055）

### 簇三：状态迁移无守卫、无必带证据

B3 未经人工评审即标 done；回链（run、branch）恒空且不随重派更新；未派发项无任何关闭通道。根因：设计了门判据，但从未回答**每个迁移允许谁写、必须带什么证据**。对策：02 章「状态迁移守卫」表——done 只能由带 PASSED verdict 的评审驱动，agent 交付止于「待人工评审」；回链是迁移必填载荷；人工流转与关闭走受守卫 action（强制 reason、写审计）。（SDLC-045/053/056/044）

### 簇四：遥测与身份无单一事实源

同一份 27B 权重以 4 个名字服务（含 2 个 claude-\* 假名）；spawn 的 tokens_output 物理不可能、tokens_input 恒 0；harness 包被重部署抹掉后 brain 静默换引擎跑了一整天。根因：模型身份、用量、引擎形态各自散落，没有权威登记处。对策：04 章模型注册表（真名+别名映射，假名即拒绝）、用量采集契约（只取流终 usage、超物理速率标 suspect 不入度量）、降级显式化不变量（静默降级本身定性为缺陷）。（SDLC-046/048/049/051/054）

### 簇五：引擎终态传导不完备

reconcile 判死 spawn 后节点悬挂 running：不可 retry、不再入队，只能整 run 取消重派；runCancel 生效却报错。根因：R1 只设计了"进程重启"场景，spawn 终态从任何来源都必须传导到 node 这一**不变量**没写成设计承诺。对策：02 章 R9——"不存在 spawn 已终态而 node 仍 running 超过一个 tick"，违反由 reconciler 修正并告警。（SDLC-050）

### 簇六：人工工作流未在 UI 一等化

自举里人工评审、合并、建 issue、关 sprint 全程走 SSH 与 MCP，页面一次没用上。根因：v2.1 把人想象成"审批者"（签核与裁决），实战中人是"评审员加策展人"——评审 agent 交付的代码、管理问题池这两个高频动作没有页面路径。对策：03 章收件箱新增**评审请求**类别（分支 diff、测试证据、审查三问、批准合并/驳回返工）；工作项状态 PropRow 变为受守卫流转入口；规划工作台观察问题池泳道。验收标准升格：**每个人工动作必须有页面路径**。（SDLC-056、SDLC-029）

### 簇七：全局标识无分配权威

itemKey 跨 sprint 重号（本章写作当天再次复发：两个不同 issue 同挂 SDLC-056）；迁移版本号跨分支静默碰撞后被静默跳过。根因：顺序小整数由各写入方自行 max+1，并行分支下必然撞号。对策：02 章「标识分配权威」——一切全局单调标识单点分配（DB 序列/advisory lock），撞号在分配时失败出声。（SDLC-037/038）

### 簇八：spec 作者 = 评审者的结构性盲区

B2 非事务三连写、B3 N+1 与吞异常都是 brain 自己写进 spec 的设计决定，brain 评审对应 diff 时零命中；而它评审**他人**遗留代码（M3-D）抓出 5 个真 bug 含 critical。评审能力没问题，**结构**有问题：没有人会质疑自己十分钟前的设计决定。对策：02 章「评审独立性」——reviewer 会话必须独立于 spec 作者，输入含需求原文，明确要求对抗性质疑 spec 本身。

### 簇九：任务规模无分流阈值

1–6 文件级 spec 下 vLLM 一次交付扎实；12 文件级（655/846 行 spec）连续 3 次输出预算耗尽、6 线程才交付，brain 被迫代写 4 个文件。根因：工作流选择器按类型分流，从未按规模分流；A10 的粒度假设没有机制强制。对策：02 章「拆分契约」——超过 6 文件或跨生命周期协同强制拆分；执行期预算耗尽两次自动回规划。

### 簇十：dev 执行器无上下文管理

worker 是一根裸循环：消息只增不减，溢出物理窗口即截断失败，重试从零重跑——确定性再溢出。brain 有自动压缩，worker 没有：**上下文能力不对等**，设计从未考虑执行器的上下文生命周期（R1–R8 全部着眼进程与状态，没有一条管窗口）。对策：02 章「执行器上下文契约」C1–C4——工具结果窗口化、超阈自动折叠、截断续写（携带已完成产物）、与拆分契约互补。
