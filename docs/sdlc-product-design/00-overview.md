# 00 · 总体设计：愿景、原则与系统全景

## 1. 愿景

**人负责说清楚，系统负责做出来，并且自己证明做对了。**

这套系统把已经在实践中验证过的 agentic-engineering SDLC 工作流，从
"Claude Code 技能 + 脚本 + GitLab 标签"形态，升级为运行在 agent-native
四个应用之上的一等系统能力：

- 人的时间只花在**判断**上：把需求说清楚、把范围划清楚、审查 UI 设计、
  审查技术设计、审查测试计划——这些步骤有专门设计的、一次一问带推荐答案的
  交互界面，而不是在聊天窗口里自由发挥。
- 判断完成之后**全自动执行**：编排器按可复用的 DAG 工作流派发、开发、测试、
  评审、管理 issue、记录测试证据、合入交付，全程状态自动回写，人只在
  升级（escalation）时被打断。
- 全程**证据优先**：每一次"完成"都必须附带可核对的证据
  （`repo:file:line`、PR 链接、真实运行输出、截图），拒绝一切
  "implemented / done / ✓" 式的自我宣称。

## 2. 五条产品立场（区别于"把任务丢给 AI"）

1. **不是把任务丢给 brain 让它自己设计自己开发。** 规划阶段（sprint 规划、
   需求明确、UI 设计评审、技术设计评审、测试计划评审）是人主导、系统辅助的
   结构化交互；只有全部签核后，工作才进入自动执行域。
2. **brain 可替换，hand 可多样。** 编排大脑（今天是 Claude Code，明天可以是
   任何 ACP agent 或 SDK 模型）只做编排叙述与判断；确定性调度、状态机、
   回写全部由不依赖 LLM 的协调器完成（homerail 的双脑分层）。工人节点
   按任务选模型（本地 vLLM 为主力，按仓可切换）。
3. **简单任务走短流程。** 工作流是数据不是代码：完整 SDLC、快速任务、
   缺陷热修、文档任务、调研任务各有可复用模板，按工作项类型自动选择、
   可人工覆盖。不强迫一行文案改动走七个阶段。
4. **UI 设计是流程的一等公民。** 原 SDLC 从 sprint-plan（what/why）直接跳到
   sprint-design（where/how），中间没有任何"用户会看到什么"的设计环节——
   这是实践中已知的最薄弱点。v2.0 在两者之间补上 UI 设计子流程：
   ui-spec 产物 → design 应用原型流水线 → 嵌入式 UI 评审 → ui-signoff，
   技术设计与测试场景引用原型而非凭空想象界面。
5. **系统的核心价值是可视化与交互，不是流程搬家。** 我们不是把 SDLC 的
   markdown 平移进数据库——原来"一大堆文字没人细看"的测试计划、技术设计、
   依赖关系、数据模型，要变成场景卡、DAG 图、模型图、可嵌入原型这样
   **可视化、可交互**的呈现，让人真的去理解与审查；而 agent 拿到的永远是
   干净的纯文本/结构化数据——复杂呈现只给人，绝不进 agent 上下文。

## 3. 设计原则（约束所有模块设计）

| #   | 原则             | 来源               | 含义                                                                                                                                                                    |
| --- | ---------------- | ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P1  | 四位一体         | agent-native       | 每个功能必须同时落 UI、actions、技能/指令、application state；agent 与 UI 能力对等                                                                                      |
| P2  | 双脑分层         | homerail           | LLM 只做规划与判断；调度/状态机/回写是确定性代码，可测试、可重放                                                                                                        |
| P3  | 最小知识契约     | homerail / a-e     | 工人只看自己的 brief 与依赖产物，永远拿不到全图与 sprint 文档；上游到下游只走显式声明的数据边                                                                           |
| P4  | 证据优先         | a-e 验证纪律       | 引用即打开；反奉承 schema；宣称者与批准者分离；真实运行证据                                                                                                             |
| P5  | 有界自愈         | homerail / a-e     | 纠偏、重试、评审、审计全部有硬上限，超限升级人类，绝不无限自旋，也绝不静默挂死                                                                                          |
| P6  | 产物即接口       | a-e                | sprint 文档、测试计划、ui-spec、技术设计、briefs、审计报告都是版本化产物，有明确 schema，人写产物受保护                                                                 |
| P7  | 工作流即数据     | v1.1 §3.8          | 流程逻辑放在版本化 DAG 模板与技能 markdown 里，改流程不改代码；进代码的只有能力原语                                                                                     |
| P8  | 幂等与可恢复     | homerail / v1.1    | 一切推进操作幂等 + 前置断言；进程重启可从持久化事件恢复；孤儿运行态降级而非悬挂                                                                                         |
| P9  | 乐观与密度       | multica            | UI 点击即改、乐观更新、失败回滚；Linear 级信息密度；渐进披露，过程可折叠、结论外露                                                                                      |
| P10 | 状态可感         | multica            | 系统任何"正在发生"都有专门的视觉语汇（流光、呼吸、计时器、状态环），人扫一眼就知道系统在不在动、卡在哪                                                                  |
| P11 | 双表征           | 本设计             | 每份产物同源两个视图：人审查用富可视化（content 的表格/折叠/图/清单 block），agent 消费用纯文本（tracker 产物列 / pull-document 纯文本）；渲染永不反向污染 agent 输入   |
| P12 | 低摩擦保底       | 本设计             | 结构化流程的每一步都有跳过与直达通道：可选步骤（头脑风暴）、手工导入现成文档、直接建单直接派发；原来容易做的事进了系统必须仍然容易                                      |
| P13 | 机制优先于提示词 | v2.2 自举（07 章） | 凡红线，必有一个技术机制背书——能力面裁剪、写入守卫、引擎断言、显式告警四者其一；提示词只承担解释职责。可观察 ≠ 已约束；自举证明纯提示词红线在压力下必然失守（SDLC-052） |

## 4. 系统全景

### 4.1 四应用分工

```
┌───────────────────────────── 人（判断） ─────────────────────────────┐
│   规划访谈 · 需求定稿 · UI 评审 · 技术设计评审 · 测试计划评审 · 签核    │
└──────────────────────────────┬───────────────────────────────────────┘
                               │
┌──────────────────────────────▼───────────────────────────────────────┐
│ TRACKER · 流程域驾驶舱（单一事实源：该做什么、做到哪、谁批准）           │
│  项目/仓库注册 · Sprint(phase 权威) · Epic/工作项 · 依赖图+校验          │
│  规划工作台(技能链) · 产物库(版本化) · 审批中心 · 依赖感知调度 · 度量     │
└───────┬──────────────────────────────────────────────▲───────────────┘
        │ 派发（MCP：brief 全文入 inputs，                │ 确定性回写
        │ tags 带 ownerEmail/orgId/ids）                  │（reconciler → tracker-client，
        │                                                │  get-activity 轮询兜底）
┌───────▼──────────────────────────────────────────────┴───────────────┐
│ ORCHESTRATOR · 执行域引擎室（怎么做、哪个沙箱、哪个模型）                │
│  V3 DAG 引擎(可视化) · 工作流库(多套模板,版本化) · Brain(可替换)          │
│  Worker(vLLM 主力/按仓切换) · Workspace · PR/CI/合并 · 健康门 · 洞察     │
└───────┬───────────────────────────────┬───────────────────────────────┘
        │ A2A（ui-spec → 原型流水线）      │ A2A（story/changelog → 文档）
┌───────▼───────────────┐       ┌───────▼───────────────┐
│ DESIGN · UI 域         │       │ CONTENT · 文档域       │
│  设计系统(Foundry)      │       │  交付文档 · 发布说明    │
│  Sprint 原型(多屏)      │       │  验收报告归档           │
│  UI 评审(批注)          │       │  产品知识沉淀           │
└───────────────────────┘       └───────────────────────┘
```

分工裁决（继承 v1.1 §3.1，扩展 design/content）：

- **tracker 拥有**：该做什么（工作项/依赖）、做到哪（sprint.phase 权威 + 阶段派生）、
  谁批准（审批门）、产物库、度量。
- **orchestrator 拥有**：怎么做（DAG 模板）、哪个沙箱（workspace）、哪个模型
  （agent 定义 + 运行时配置）、执行证据的原始记录。
- **design 拥有**：设计系统、sprint 原型（每 sprint 一个 design，多屏）、
  UI 评审的画布与批注。
- **content 拥有**：面向人的交付文档（story、changelog、发布说明）、验收报告
  归档、长文档。
- 跨应用只传 **id + 有界全文**（brief、ui-spec 是有界文档，直接入 run inputs；
  原型传 designId + 深链，不把 HTML 塞进 prompt）。

### 4.2 身份与安全（继承 v1.1，全景重申）

- 所有跨应用调用走 A2A/MCP + `A2A_SECRET` JWT，run tags 携带
  `{source, sprint_id, item_id, ownerEmail, orgId}`，回写通道用 tags 中身份铸 JWT，
  保证 ownable 数据落在正确 org。
- brief 隔离改为**按工作流声明的载荷契约**（02 §3 契约表）：issue-pipeline
  工人只许 brief / shared-brief / ui-spec 屏摘要；sdlc-verify 追加 test-plan
  场景节；sdlc-gap-analysis 追加 sprint-doc 的 Goal 与指标节（goal-metrics
  节选）。任何工作流都禁止注入 technical-design 全文与 issue 清单；
  "节选"是确定性提取的结构化节，不是全文。
- workspace 临时 token、commit 前密钥扫描、`*.mcp.json` 排除、日志脱敏，
  全部继承现有实现并在 UI 中可见（工作区页显示扫描结果）。

## 5. 端到端旅程：一个 Sprint 的完整故事

五条泳道：人 · Tracker · Design · Orchestrator · Content。
旅程分七步呈现；与 02 章八相位状态机的对应：②③ 同处 designing 相位、各自签核（技术设计依赖已签核的 ui-spec，顺序在 UI 之后），⑦ 覆盖 promoting、storytelling、done，其余一一对应；⑤ 的 RED 回环是相位内修复，verifying 不回退。

```
阶段        人                        Tracker                Design           Orchestrator            Content
────────────────────────────────────────────────────────────────────────────────────────────────────────────
① 规划      /brainstorm 对话(可选)    brainstorm-notes 产物(可选)
            /sprint-plan 访谈         sprint-doc v1(human，含 Goal
                                      与可证伪成功指标——全程完成判据的锚)
            /sprint-test-plan 审查    test-plan 产物
            ▶ plan-signoff 签核       phase: planning→designing
────────────────────────────────────────────────────────────────────────────────────────────────────────────
② UI 设计   （含 UI 的 sprint）        ui-spec 产物            sprint 原型
            在评审屏逐屏批注           批注→ui-spec 修订        (sdlc-ui-build ──▶ 原型生成流水线
            ▶ ui-signoff 签核                                  多屏原型)          (vLLM 并行出屏)
────────────────────────────────────────────────────────────────────────────────────────────────────────────
③ 技术设计  审查设计草稿               technical-design v1(agent)                    /sprint-review 对抗评审
            看对抗评审报告             technical-design v2(评审修订)                  (vLLM/sonnet 交替轮)
            ▶ design-signoff 签核     briefs 提取(确定性)
                                      依赖图校验 · phase→executing
────────────────────────────────────────────────────────────────────────────────────────────────────────────
④ 实施      （不介入）                依赖感知调度：解锁即派发                    sdlc-issue-pipeline × N
                                      状态/证据自动回写                          dev→qa→reviewer→gatekeeper→
                                      看板卡片实时前进                           diff-audit→PR→CI→合入
────────────────────────────────────────────────────────────────────────────────────────────────────────────
⑤ 验证      （不介入）                verify-report 产物                        sdlc-verify：全量测试+
                                      RED→自动建 from-audit 单                  集成场景逐个实测
                                      修复单自动派发(阶段子集)
────────────────────────────────────────────────────────────────────────────────────────────────────────────
⑥ 目标审计  仅在 3 轮超限时裁决        audit-report:{n} 产物                     sdlc-gap-analysis：
  (gap-analysis)                      NO_GAPS→phase→promoting                  按 Sprint Goal 逐指标判
                                                                               MET/UNMET(证据 schema，反奉承)
────────────────────────────────────────────────────────────────────────────────────────────────────────────
⑦ 交付      验收 story                phase→done                               sdlc-promote：拓扑序      story/changelog
            （或 accept/defer）        度量页更新                                merge-commit 晋升         发布说明入库
────────────────────────────────────────────────────────────────────────────────────────────────────────────
```

**人工介入只出现在**：①②③ 的访谈与三道签核、⑥⑦ 的例外裁决，以及任何
escalation。其余全部自动。这与 v1.1 M0 对齐口径一致，v2.0 增加了 ② 这道
可选的 UI 签核。

**Sprint 的完成由 Goal 判定，不由"单子关完"判定**（承 a-e Phase H 纪律：
closed ≠ goal achieved）：① 定下的 Goal 与可证伪指标是唯一基准，⑥ 的
gap-analysis 只看 Goal + 跨仓 diff + 验证日志（不看 issue 清单），逐指标给出
MET/PARTIAL/UNMET 与证据，verdict=NO_GAPS 是晋升合入 base 的前置条件。

## 8. 假设与前提

本设计的全部结论建立在以下假设之上。任何一条失效，对应模块需要重估
（括号内为受影响章节）。

**环境与运行时**

| #   | 假设                                                                                                                                                | 失效影响                                      |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------- |
| A1  | 部署形态是 101 单机 docker compose（an-\* 容器 + 共享 Postgres + nginx 网关）；hosted/多租户不是当前目标，但 schema 与访问控制仍按 ownable 规范设计 | 跨机部署需重估回写通道与共享 DB 读取（02 §6） |
| A2  | 本地 vLLM（qwen3.6）持续可用且是 dev/qa 主力；sonnet 档经 API 可用于 review/gate/audit；开发阶段不引入其他外部模型                                  | 模型策略与 devModel 切换设计重估（02 §3）     |
| A3  | Claude Code 订阅只供 brain 使用：不给 worker、不高频轮询 usage（账号安全红线）                                                                      | brain 引擎默认项与健康门语义变化（02 §5）     |
| A4  | 浏览器可出网加载 CDN（Tabler / Google Fonts / Alpine）；原型与 design 渲染依赖之                                                                    | 离线环境需把资源内联进设计系统（01 §6）       |

**流程与组织**

### 8.1 自举修订（v2.2）——被实战证伪或需强化的假设

2026-07-11 自举实战（07 章）对上表的修订，以及此前**隐含未写出**、
失效后才暴露的假设——现补为显式假设并配机制：

**既有假设修订**

- **A2 修订**：模型"身份"不可假设——本地 vLLM 曾以 4 个名字（含 2 个
  claude-\* 假名）服务同一份权重（SDLC-054）。模型真名+别名映射必须由
  注册表权威登记（04 §7），归因/度量只认真名。
- **A12 修订**：引擎"既有能力保持可用"不等于"行为正确"——spawn 终态
  传导（SDLC-050）、用量采集（SDLC-051）都需以不变量+告警背书
  （02 §4 R9、04 §13），能力存在性不再当作正确性证据。
- **A18 修订**：时间戳可信，但 **token 用量列在采集契约（04 §13）修复
  前不得进入任何度量**——现值物理不可能（SDLC-051）。

**新增显式假设（此前隐含，自举证伪后补写并配机制）**

| #   | 假设                                                                                                  | 失效影响                                                       |
| --- | ----------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| A21 | 工作区由供给管道保证：基线新鲜、依赖预热、测试可执行（02 §7 三不变量）；不满足即 infra 故障，不开 run | 全部执行工作流的交付质量失去地基（曾以 SDLC-056/057 形式失效） |
| A22 | agent 的能力边界由机制（能力面矩阵 02 §5.4）而非提示词保证；提示词红线单独存在时视为未设防            | 作者身份/审计链失真（曾以 SDLC-052 形式失效）                  |
| A23 | 状态迁移只接受守卫表（02 §8）列明的写入方与证据载荷；其余写入一律拒绝                                 | done 失去含义、回链断裂（曾以 SDLC-053/056 形式失效）          |

## 10. 术语表

| 术语                | 定义                                                                                                               |
